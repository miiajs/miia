`@miiajs/messaging-redis` is the production transport for [`@miiajs/messaging`](/docs/packages/messaging). It implements the same `MessageTransport` interface as the in-memory default, so user code does not change - only the transport factory passed to `MessagingModule.configure`. Reach for it as soon as you need persistence, multi-replica deployments, or crash recovery.

Under the hood it uses Redis Streams with consumer groups, the group's own pending entries list (PEL) as the retry queue, and atomic Lua scripts for the nack and DLQ transitions.

## Installation

::code-group

```bash [bun]
bun add @miiajs/messaging-redis ioredis
```

```bash [npm]
npm install @miiajs/messaging-redis ioredis
```

```bash [pnpm]
pnpm add @miiajs/messaging-redis ioredis
```

```bash [yarn]
yarn add @miiajs/messaging-redis ioredis
```

::

`ioredis` is a peer dependency - install it explicitly so your app pins the version. The transport is tested against `ioredis@^5`.

**Redis 6.2 is the hard minimum, 7.0 or newer is recommended.** Retry needs `XPENDING ... IDLE` and the exclusive `(<id>` cursor, both of which landed in 6.2. On 7.x an entry trimmed out of the stream while still pending disappears from the PEL; 6.2 keeps the PEL row and answers a claim with `[null]`, which the transport acks away as a ghost. The package's own test suite runs against `redis:7-alpine`.

## Setup

```typescript
import { Module } from '@miiajs/core'
import { MessagingModule } from '@miiajs/messaging'
import { redisStreamsTransport } from '@miiajs/messaging-redis'

@Module({
  imports: [
    MessagingModule.configure({
      transport: redisStreamsTransport({
        url: 'redis://localhost:6379',
      }),
    }),
  ],
})
class AppModule {}
```

With `ConfigService` for env-driven URLs:

```typescript
import { ConfigService } from '@miiajs/config'

MessagingModule.configure((resolve) => ({
  transport: redisStreamsTransport({
    url: resolve(ConfigService).getOrThrow('REDIS_URL'),
    retry: { maxAttempts: 10 },
  }),
}))
```

Everything else from [the Overview page](/docs/packages/messaging) - `@On`, groups, retry/DLQ, `MessageBus.publish` - works identically.

## redisStreamsTransport options

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `url` | `string` | - | Redis URL. Mutually exclusive with `client`. |
| `client` | `Redis` | - | Pre-built ioredis instance. The transport does **not** call `connect()` or `quit()` on a user-supplied client - see [Pre-built ioredis client](#pre-built-ioredis-client). |
| `retry` | `Partial<RetryConfig>` | `DEFAULT_RETRY` | Override individual retry fields (`maxAttempts`, `backoffMs`, `backoffMultiplier`, `dlq`). |
| `retryIntervalMs` | `number` | `1000` | Housekeeping cadence: one `XPENDING ... IDLE <horizon>` sweep per `(topic, group)` per tick, then claim and redeliver. A parked retry only fires on a tick, so this is both the granularity of backoff timing and, together with the horizon, the granularity of crash detection. |
| `minIdleMs` | `number` | `60000` | Floor for the [retry horizon](#the-horizon). The horizon is `max(minIdleMs, every backoff level)`, so lowering this below your largest backoff changes nothing. |
| `blockMs` | `number` | `5000` | `XREADGROUP BLOCK` timeout. Governs idle Redis traffic and the retry cadence after a transient connection error, nothing else - new messages wake the blocked read immediately, publish latency is unaffected thanks to the [connection model](#connection-model), and `onDestroy()` disconnects the socket rather than waiting the block out. |
| `drainTimeoutMs` | `number` | `5000` | One budget covering the running housekeeping pass **and** the in-flight handlers, before `onDestroy()` forces cleanup. `0` skips the drain. See [Graceful drain](#graceful-drain). |
| `consumerName` | `string` | `${hostname}:${pid}:${rand8}` | Override for the auto-generated consumer name. Useful for diagnostics. |
| `retrySchedulerIntervalMs` | `number` | - | **Deprecated** alias of `retryIntervalMs`. |
| `reclaimIntervalMs` | `number` | - | **Deprecated** alias of `retryIntervalMs`. Its own default used to be `30000`. |

::warning
**`retrySchedulerIntervalMs` and `reclaimIntervalMs` are deprecated.** Retry scheduling and idle reclaim are [one pass](#crash-recovery) now, so the two timers collapsed into `retryIntervalMs`. Both old names are still honored and log a deprecation warning; precedence is `retryIntervalMs` > `retrySchedulerIntervalMs` > `reclaimIntervalMs`. The first of the deprecated pair drove retry cadence, which is what the surviving timer does.

The default dropped from 30s to 1s because that timer now carries retry as well as reclaim. If you had tuned only `reclaimIntervalMs: 30000`, you keep the 30s cadence you asked for - which is 30x worse retry latency than the new default. Rename the option and pick the interval you actually want.
::

## Connection model

The transport keeps **one publisher client** for `XADD`, `XACK`, all Lua commands (`parkRetry` / `drainRetry` / `moveToDlq`), `XGROUP CREATE`, the housekeeping sweep and the heartbeat. Every `subscribe()` call additionally creates its **own duplicated client** per lane via `pubClient.duplicate({ lazyConnect: true })` and runs its blocking `XREADGROUP` loop on it.

```
┌─────────────────────────────────────────────────────┐
│ pubClient            (1 socket)                     │
│   ├─ XADD            (publish)                      │
│   ├─ XACK            (per-message ack)              │
│   ├─ Lua scripts     (parkRetry, moveToDlq)         │
│   ├─ XPENDING/XCLAIM (housekeeping sweep)           │
│   └─ XCLAIM JUSTID   (heartbeat)                    │
├─────────────────────────────────────────────────────┤
│ subClient #1         (1 socket per lane)            │
│   └─ XREADGROUP BLOCK <ms>                          │
│ subClient #2                                        │
│   └─ XREADGROUP BLOCK <ms>                          │
│ ...                                                 │
└─────────────────────────────────────────────────────┘
```

Why split the connection: ioredis serializes commands on a single TCP socket, and `XREADGROUP ... BLOCK <ms>` holds the socket until data arrives or the timeout fires. Sharing one connection for publishing and blocking subscribers would queue every `XADD` behind the in-flight BLOCK, with publish latency growing linearly in subscriber count. Per-subscribe duplicates make publish latency constant (≈ network RTT), regardless of how many topics × groups you subscribe to. This is the same pattern BullMQ uses for its workers.

Connection count: `1 (publisher) + Σ handlers × max(1, sliding lane count)`. Each `@On` is its own subscription, so handler count is the multiplier - batch handlers add one connection each, sliding handlers add `concurrency` connections each. Earlier versions collapsed several `@On` sharing a `(topic, group)` pair into a single subscription; each is now its own, trading connection budget for delivery isolation. Replicas multiply this by replica count, but consumers within an auto-derived group share that group's broker round-robin (replicas don't multiply broker-side group count - just consumer count within each group). `redisIdempotencyStore` keeps its own client and adds to the count separately. SubClients are owned by the transport regardless of `ownsClient` - the `ownsClient` flag only governs the user-supplied parent client; duplicates are always created and closed by us. Lua scripts are registered per instance on the parent client only; lane clients never run anything but `XREADGROUP`, so they do not need them.

::warning
**Cost warning for managed Redis tiers.** Combining bus-default sliding with many handlers is multiplicative. Example: 10 handlers and `MessagingModule.configure({ dispatch: { mode: 'sliding', concurrency: 4 } })` produces 41 connections per replica (1 publisher + 10 × 4 lanes). Managed providers like Upstash and Redis Cloud price by connection count. Recommendation: leave the bus default at `batch`, opt into `mode: 'sliding'` only on individual handlers with variable runtime characteristics.
::

### Broadcast group lifecycle

Each handler with `broadcast: true` derives its consumer group as `<base>__<hostname>_<pid>`. On graceful shutdown (`onDestroy`), the transport runs `XGROUP DESTROY` on those groups so they don't leak. For ungraceful exits (process crash, OOM kill), the next process to subscribe with broadcast on the same hostname scans `XINFO GROUPS` and destroys any matching `<base>__<thishost>_<otherpid>` groups - cleanup happens automatically on first restart.

Limitations: cleanup only matches same-hostname orphans. If a broadcast handler ran on host A, the host went away, and the same code starts on host B, the host-A groups remain orphan in Redis. Run a periodic cleanup script if your topology has dynamic hostnames.

## Dispatch modes

Redis Streams supports both [dispatch modes](/docs/packages/messaging#dispatch-modes) - `'batch'` (default) and `'sliding'`. The choice trades latency under variable handler runtimes against the number of Redis connections held open.

### Batch (default)

A single consumer loop reads up to `concurrency` messages per `XREADGROUP COUNT=concurrency` call, runs them through `Promise.allSettled`, then reads again. That `allSettled` is the head-of-line barrier, accepted deliberately: the slowest handler in a batch holds back the next read.

```
subscription (1 connection)
  └─ XREADGROUP COUNT=4 BLOCK 5000  ──► [m0, m1, m2, m3]  ──► allSettled
                                                              │
                                                              └──► next XREADGROUP
```

Best for high-throughput uniform workloads where per-message variance is small. One connection per subscription regardless of `concurrency`.

### Sliding

`concurrency` parallel lanes, each on its own duplicated Redis connection running `XREADGROUP COUNT 1` with a unique consumer name suffix `:laneN`. Redis distributes pending entries across the lanes (since they all join the same group), so each lane only ever holds one in-flight message and the batch barrier degenerates to a single message. A slow message on lane 0 does not block lanes 1-N.

```
subscription (4 connections, mode='sliding', concurrency=4)
  ├─ XREADGROUP COUNT=1 (consumer :lane0)  ──► m0  ──► next read
  ├─ XREADGROUP COUNT=1 (consumer :lane1)  ──► m1  ──► next read
  ├─ XREADGROUP COUNT=1 (consumer :lane2)  ──► m2  ──► next read
  └─ XREADGROUP COUNT=1 (consumer :lane3)  ──► m3  ──► next read
```

Best when handler runtimes vary and you cannot tolerate one slow message stalling the others. Mirrors the BullMQ worker pattern.

### Picking a mode

| | Batch | Sliding |
| --- | --- | --- |
| Connection budget per subscription | 1 | `concurrency` |
| Behavior under runtime skew | head-of-line blocking | independent lanes |
| Best fit | uniform workloads, high message volume | mixed workloads, latency-sensitive paths |

```typescript
MessagingModule.configure({
  transport: redisStreamsTransport({ url: process.env.REDIS_URL! }),
  dispatch: { mode: 'sliding', concurrency: 4 }, // bus default
})

@On('order.placed', { mode: 'sliding', concurrency: 8 }) // per-handler override
async onOrder(order: Order) { ... }
```

Lane consumer names show up in `XINFO CONSUMERS <stream> <group>` as `${baseConsumer}:lane0`, `${baseConsumer}:lane1` etc, which makes lane-level diagnostics straightforward. Redeliveries from the [housekeeping sweep](#retry-mechanics) do not use a lane - they run under `${baseConsumer}:retry` and are capped by the subscription's `concurrency`, so a large batch of abandoned entries cannot run more handlers at once than a normal read would.

::tip
Lane count equals `concurrency` in sliding mode - size it for the **expected parallelism within a single replica**, not for total cluster throughput. Add replicas to scale horizontally; raise sliding `concurrency` to soak up runtime variance per replica.
::

## Consumer groups and deployment

Consumer groups are how Redis Streams maps logical roles to running replicas. The deployment story is straightforward:

- **One consumer group per logical role.** `email-workers`, `analytics`, `audit-log` - pick names that describe the *job*, not the host.
- **Every replica of the same role joins the same group.** Redis automatically load-balances messages across consumers within a group, so adding replicas scales throughput linearly until a single message is no longer the bottleneck.
- **Fan-out across groups is automatic.** Two `@On('user.created', { group: 'email-workers' })` handlers in one app + two `@On('user.created', { group: 'analytics' })` handlers in a different app = both groups receive every message, independently.

The most common misconfig is mixing up consumer names and group names. **Group names are shared across replicas** (that's what enables load balancing). **Consumer names must be unique per replica** - the transport defaults to `hostname:pid:rand8` which is safe by construction; only override `consumerName` if you have a reason. See [Groups and fan-out](/docs/packages/messaging#groups-and-fan-out) on the Overview page for the full mental model.

## Retry mechanics

**The group's pending entries list is the retry queue.** A nack acks nothing and re-publishes nothing: the entry stays pending in the PEL of the group that read it, and resurfaces one backoff later for that group only.

```
XADD ──► XREADGROUP '>' ──► handler ──► ack ──► XACK  (done)
                              │
        attempts left         ├──► XCLAIM ... IDLE <horizon - backoff> JUSTID
                              │       (still pending in THIS group's PEL)
                              │                     │
                              │                     ▼  every retryIntervalMs
                              │     XPENDING ... IDLE <horizon> ──► XCLAIM ──► handler
                              │
        budget spent          └──► XACK + XADD <topic>.dlq   (one Lua step)
```

Step by step:

1. `XADD <topic>` writes the envelope as a stream entry.
2. A consumer reads via `XREADGROUP GROUP <group> <consumer> COUNT <n> BLOCK <ms> STREAMS <topic> >`. `>` only ever yields entries never delivered to this group, so the delivery count is 1 and so is `meta.attempt`.
3. On ack: a single `XACK <topic> <group> <id>` removes the entry from the PEL. Nothing else happens.
4. On nack with attempts left, the `parkRetry` Lua script runs `XCLAIM <topic> <group> <consumer> 0 <id> IDLE <horizon - backoff> JUSTID`. No `XACK`, no `XADD`. `JUSTID` skips the payload in the reply and does not increment the delivery count - parking is not a delivery. The entry now reports `horizon - backoff` ms of idle time, so it crosses the horizon exactly one backoff later. The script is gated on this consumer still owning the entry, so a process whose heartbeat lapsed cannot steal back an entry another replica has legitimately reclaimed.
5. Every `retryIntervalMs`, the housekeeping pass sweeps each subscribed `(topic, group)`: `XPENDING <topic> <group> IDLE <horizon> - + <count>`, paged with an exclusive `(<id>` cursor, skipping entries this process is still handling. Each match is claimed with `XCLAIM ... <horizon>` and redelivered. The claim is the mutual exclusion: it resets idle to zero, so a concurrent pass on another replica gets an empty reply instead of a second delivery.
6. On nack with the budget spent (`attempt >= maxAttempts`), the `moveToDlq` Lua script runs `XACK` on the original entry plus `XADD <topic>.dlq` with `meta.lastError` filled in. The `XACK` return value gates the `XADD`, so two replicas reaching the same exhausted entry in one window write exactly one DLQ record. With `retry: { dlq: false }` the entry is acked and the failure logged instead.

Both transitions use Lua scripts (registered via ioredis `defineCommand` and cached server-side via EVALSHA) because each couples two Redis operations that must succeed or fail together, and because both decisions are reachable by several replicas at once.

`XCLAIM` bumps the delivery count by exactly one, and the post-claim count equals the number of times the handler has run. That is the invariant behind `meta.attempt`: the attempt number a redelivery carries is the pre-claim delivery count plus one. The one exception is a record read off a `<topic>.dlq` stream, whose `meta.attempt` describes the death of the original message and is left alone - reading a DLQ record can never look like a fresh exhaustion.

### Why the PEL and not a scheduler queue

The previous design acked the entry and re-published it with `XADD`. Every consumer group on a topic sees an `XADD`, and each `@On` handler derives its own group, so multi-group topics are the norm rather than the exception - which made one handler's retry a duplicate delivery for every other handler on that topic. Keeping the retry pending in its own group's PEL and redelivering only through that group's `XCLAIM` is what makes multi-group topics safe. The suite pins this as a regression test: a retry in one consumer group is never redelivered to another group on the same topic.

### The horizon

The horizon is the idle threshold at which a pending entry counts as due:

```
horizon = max(minIdleMs, every backoff level below maxAttempts)
```

- A backoff is expressed as `IDLE horizon - backoff`, so the horizon has to cover every level. Redis clamps a deadline in the future to `now`, so a level larger than the horizon would silently collapse into an immediate retry.
- It is the `max()` of *all* levels, not the last one: `backoffMultiplier` below 1 is legal and unvalidated upstream, which makes the last level the smallest.
- Levels stop one short of `maxAttempts` - that attempt is dead-lettered, never parked.
- Idle time is measured by Redis's own clock. Sending an absolute deadline instead would fold a few seconds of clock skew between the app and Redis either into a near-zero backoff or into a full horizon.
- Because the horizon is a `max()`, lowering `minIdleMs` below your largest backoff level changes nothing.

::warning
**The horizon has a 24h ceiling, enforced at construction.** Redis accepts an out-of-range `IDLE` without complaint: pass it `9007199254740991` and the entry reports ~1ms of idle forever, matching no sweep and hanging in the PEL indefinitely. Because that failure mode is silent, `redisStreamsTransport()` throws when the computed horizon exceeds 24h instead of clamping into it. Lower `retry.backoffMs`, `retry.backoffMultiplier`, `retry.maxAttempts`, or `minIdleMs`.
::

### The heartbeat

Every `horizon / 2` (floor 50ms), the transport sends one `XCLAIM <topic> <group> <consumer> 0 <ids...> IDLE 0 JUSTID` per `(topic, group, consumer)` covering every entry it is still handling, batched at 100 ids per call. Resetting idle to zero is what frees a handler from having to finish inside the horizon - without it, a handler that runs longer than the horizon would have its own entry swept out from under it and redelivered on another replica. It is the same mechanism as BullMQ's `lockDuration` / `lockRenewTime`.

::warning
**Same stalled-job caveat as BullMQ.** The heartbeat is a `setInterval` in the same process, so a CPU-bound handler - or anything else that blocks the event loop for longer than `horizon / 2` - never gets to send it. Another replica then legitimately claims the entry and the message is processed twice. Keep long CPU-bound work off the event loop, or raise `minIdleMs` so the horizon comfortably exceeds the worst stall you can produce.
::

## Crash recovery

Retry and crash recovery are **one mechanism**. To the housekeeping sweep, a retry whose backoff has elapsed and an entry whose consumer died are indistinguishable - both are pending entries idle past the horizon, and both are claimed and redelivered by the same code. There is no separate reclaim path that can be forgotten and no second counter to keep in sync, so the backoff tests and the dead-consumer tests in the suite exercise the same sweep.

Worst-case detection latency after a consumer dies:

```
horizon + retryIntervalMs   =   60s + 1s with the defaults
```

Shorten `retryIntervalMs` for faster reaction (the cost is one PEL scan per `(topic, group)` per tick), and `minIdleMs` only if it is currently above your largest backoff level - the horizon is a `max()`, so below that point it has no effect.

The attempt counter of record is the PEL delivery count, which Redis maintains. Three consequences:

- It survives the process. A replica that dies mid-handler does not reset or lose the count, which is what makes a crashed delivery resume the retry sequence rather than restart it.
- There is exactly one counter, shared by business failures and crashes. A `SIGKILL` in the middle of a handler costs an attempt. Graceful shutdown drains the handler first, so this only bites on hard kills.
- An abandoned entry whose delivery count already reached `maxAttempts` goes straight to the DLQ with a synthetic error - `Abandoned on <topic> after N delivery attempt(s) without ack or retry` - because nobody was alive to report the real one. That check runs *before* the claim, so a poison message that kills the process does not earn an extra attempt beyond `maxAttempts`.

## Stream retention

::warning
**Stream retention is load-bearing.** The retry lives in the stream entry itself, so a `MAXLEN` / `MINID` capped `XADD` or an `XTRIM` that cuts away a still-pending entry destroys the payload. On Redis 7 the entry is dropped from the PEL outright; on 6.2 the PEL row survives and a claim answers `[null]`, which the transport logs and acks away as a ghost. Either way the message is gone. The old ZSET scheduler held an independent copy of the envelope and had no such exposure.

Size stream retention to outlast your longest retry chain: `maxAttempts` levels of backoff plus the horizon, with margin for a replica being down. If you trim by length, make sure the cap is comfortably above the number of entries that accumulate over that window.
::

## Operational notes

- **`XPENDING ... IDLE` scans the whole PEL.** The `IDLE` filter is applied after the range walk and does not consume `COUNT`, so the scan is proportional to PEL size, once per `(topic, group)` per tick. Measured: 20k pending entries with zero matches costs about 3ms. Not a cliff, but it is why `retryIntervalMs` and PEL depth interact.
- **Manual Redis commands drift the attempt counter.** An operator-issued `XCLAIM` burns an attempt. `XREADGROUP ... 0` both increments the count and resets idle, which pushes every parked retry on that group out by a full horizon. `XGROUP SETID ... 0` resets the counters outright.
- **Renaming a handler orphans its parked retries.** The consumer group name is derived from the handler's class and method (and the app name, when set), so renaming any of them - or introducing `appName` - creates a new group. Retries parked under the old group become unreachable: housekeeping only sweeps groups this process is actually subscribed to. Drain the old deployment before renaming, or clean the old group up by hand.
- **`NOGROUP` shuts a lane down.** If the stream or the group is deleted underneath a running consumer, the lane exits instead of retrying against a group that no longer exists.
- **Legacy ZSET migration is transitional.** Due entries in the pre-PEL `<topic>:retry` ZSET are drained back into the main stream once per topic on `subscribe()`, then on a schedule of its own - 10s, doubling to a 60s ceiling while the key stays empty, straight back to the retry cadence as soon as a drain moves something, because an old replica is then still writing. It is off the retry tick because the key usually does not exist and probing it per `(topic, group)` per tick was two thirds of an idle transport's Redis traffic; it never backs off to zero, so a long canary is not stranded either. Unlike a PEL retry it re-adds with `XADD`, so those entries still fan out to every group on the topic. Drained envelopes carry no `lastError`, so they are delivered with a fresh attempt budget. This path is removed in the next minor.

## Graceful drain

`onDestroy()` waits up to `drainTimeoutMs` for in-flight handlers to finish before closing the Redis client. Without drain, a SIGTERM mid-handler aborts the consumer loop and quits the client while a handler is still running - the message stays un-acked, another replica's housekeeping pass picks it up once it crosses the horizon, and the work is done twice.

Drain order: `abort each subscription` → `disconnect each subClient` (forces in-flight `XREADGROUP BLOCK` to throw `Connection is closed`, the consumer loop sees the abort flag and exits cleanly) → `await the running housekeeping pass and every in-flight handler` so they finish their final `XACK` / Lua calls through the still-alive pubClient → `stop the heartbeat` → `XGROUP DESTROY` for broadcast groups → `quit pubClient` (only when the transport owns it).

Two details of that order matter:

- **One budget, not two.** `drainTimeoutMs` covers the running housekeeping pass *and* the handlers it started. A slow pass does not buy its own redeliveries a second timeout.
- **The heartbeat stops last.** It keeps running through the drain so a handler that is still finishing keeps its entry invisible to other replicas; stopping it first would expose those entries to the horizon early.

A handler that misses the drain window is not lost: its entry stays in the PEL and any replica redelivers it once it crosses the horizon. `drainTimeoutMs` sizes duplicate work, not loss.

::tip
Because subClients are forcibly disconnected on abort, shutdown is bounded by `drainTimeoutMs` regardless of `blockMs`. Size `drainTimeoutMs` to cover expected handler runtime; the previous "`drainTimeoutMs >= blockMs + handler runtime`" rule no longer applies.
::

DLQ writes during drain are safe - the `moveToDlq` Lua script is awaited synchronously inside the tracked `processMessage` promise, so the XADD to `<topic>.dlq` completes before the drain promise resolves.

## redisIdempotencyStore

Production-ready [`IdempotencyStore`](/docs/packages/messaging#idempotency) backed by Redis. Pair with any `MessageTransport` (Redis Streams, NATS, in-memory, etc.) - the store is transport-agnostic.

```typescript
import { Module } from '@miiajs/core'
import { MessagingModule } from '@miiajs/messaging'
import { redisIdempotencyStore, redisStreamsTransport } from '@miiajs/messaging-redis'

@Module({
  imports: [
    MessagingModule.configure({
      transport: redisStreamsTransport({ url: 'redis://localhost:6379' }),
      idempotency: redisIdempotencyStore({
        url: 'redis://localhost:6379',
        keyPrefix: 'orders-svc:idem:',
      }),
    }),
  ],
})
class AppModule {}
```

`claim()` is `SET <prefix><id> 1 NX EX <ttl>` - atomic, so concurrent claims for the same id produce exactly one `true`. `release()` is `DEL <prefix><id>`. Keys auto-expire after the TTL passed to `@Idempotent`.

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `url` | `string` | - | Redis URL. Mutually exclusive with `client`. |
| `client` | `Redis` | - | Pre-built ioredis instance. The store does **not** call `connect()` or `quit()` on a user-supplied client. |
| `keyPrefix` | `string` | `'miia:idem:'` | Key prefix in Redis. **Set a per-service prefix** when multiple services share a Redis instance so claims do not collide across services. |

::tip
The Redis client used for idempotency can be the **same** ioredis instance you pass to `redisStreamsTransport({ client })`. Multiplexing one connection is fine - the Redis protocol is request/response and `claim`/`release` calls are short and non-blocking. The transport never blocks on this connection: blocking `XREADGROUP` runs on isolated [per-subscribe duplicates](#connection-model), so sharing the parent client with the idempotency store (or any other subsystem) does not create publish-latency contention.
::

## Pre-built ioredis client

When you want to share a connection with other parts of your app - caching, rate limiting, session storage - pass a pre-built `Redis` instance instead of a URL:

```typescript
import { Redis } from 'ioredis'
import { redisStreamsTransport } from '@miiajs/messaging-redis'

const client = new Redis(process.env.REDIS_URL!)

MessagingModule.configure({
  transport: redisStreamsTransport({ client }),
})
```

The transport tracks an `ownsClient` flag internally:

- **`url` form:** the transport creates the ioredis instance, calls `connect()` in `onInit`, and `quit()` in `onDestroy`. It owns the lifecycle of the parent client.
- **`client` form:** the transport never calls `connect()` or `quit()` on your client. **Your code owns the lifecycle.** Initialise the connection before the app starts, and tear it down after `app.destroy()` returns.

In both cases, the transport calls `client.duplicate({ lazyConnect: true })` for every `subscribe()` to spin up a dedicated blocking client (see [Connection model](#connection-model)). Those duplicates are owned by the transport regardless of `ownsClient` - they are created and closed by us, never by your code. The `ownsClient` flag only governs the parent.

This split exists so you can multiplex the parent connection across multiple subsystems (idempotency store, cache, rate limiter) without the transport reaching in and quitting it out from under you, while still getting per-subscribe blocking isolation for free.

## Testing

Integration tests need a real Redis - `ioredis-mock` and similar libraries do not implement Streams faithfully enough for retry/DLQ semantics. The pattern used by the package's own test suite is to skip when `REDIS_TEST_URL` is unset:

```typescript
import { describe, it, expect } from 'bun:test'
import { Redis } from 'ioredis'
import { RedisStreamsTransport } from '@miiajs/messaging-redis'
import { randomUUID } from 'node:crypto'

const REDIS_URL = process.env.REDIS_TEST_URL
const d = REDIS_URL ? describe : describe.skip

d('my events integration', () => {
  it('delivers across consumers', async () => {
    const transport = new RedisStreamsTransport({
      url: REDIS_URL!,
      retry: { backoffMs: 50 },
      blockMs: 200,
    })
    await transport.onInit()
    // ... use transport ...
    await transport.onDestroy()
  })
})
```

Two operational tips:

- **Always use unique topic names per test** (UUID suffix is enough). Cross-test pollution from a leftover stream is the #1 source of flaky retry/DLQ assertions.
- **Lower `blockMs` to 200ms** in tests so `unsubscribe()` and `onDestroy()` return promptly instead of waiting for the default 5s `XREADGROUP BLOCK` to time out.

Provisioning the Redis instance itself - local container, managed service, in-cluster pod - is up to you; the transport only needs a reachable URL exported as `REDIS_TEST_URL` before the suite runs.
