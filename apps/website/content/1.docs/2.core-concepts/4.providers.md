Providers are the backbone of MiiaJS's dependency injection (DI) system. A class decorated with `@Injectable()` and declared in a module can be injected into the other classes of that module, and into modules that import it once the module exports it - see [Modules → Boundaries](/docs/core-concepts/modules#boundaries).

## Defining a provider

```typescript
import { Injectable } from '@miiajs/core'

@Injectable()
class UserService {
  findAll() {
    return [{ id: 1, name: 'Alice' }]
  }

  findById(id: string) {
    return { id, name: 'Alice' }
  }
}
```

Register the provider in a [Module](/docs/core-concepts/modules):

```typescript
@Module({
  controllers: [UserController],
  providers: [UserService],
})
class UserModule {}
```

`app.provide()` registers a provider on the app itself, outside any module - for a script or a test without modules. It does not replace what a module declares: providing a token that a loaded module declares throws, and the replacement in a test is [`override()`](/docs/core-concepts/testing#overrides):

```text
[Miia] provide(UserService): UserService is declared by UserModule - replace it with override() instead
```

A provided token has no module, so every module can see it. What the provider itself injects is checked from the [root](/docs/core-concepts/modules#the-root): it sees what the modules passed to `app.register()` export.

## Injecting dependencies

Call `inject()` in a field initializer to resolve a dependency:

```typescript
import { Controller, Get, inject } from '@miiajs/core'

@Controller('/users')
class UserController {
  private userService = inject(UserService)

  @Get('/')
  list() {
    return this.userService.findAll()
  }
}
```

## Typed tokens

A class is the simplest token: `inject(UserService)` returns a `UserService`. For a value that is not an instance of a class you register - an interface, an options object, a third-party client - create a token with `createToken<T>()` and register it with `provider()`:

```typescript
import { createToken, inject, Injectable, Module, provider } from '@miiajs/core'

interface Mailer {
  send(to: string, body: string): Promise<void>
}

export const MAILER = createToken<Mailer>('Mailer')

@Module({
  providers: [provider(MAILER, () => new SmtpMailer())],
  exports: [MAILER],
})
class MailModule {}

@Injectable()
class NotificationService {
  private mailer = inject(MAILER) // Mailer
}

@Module({ imports: [MailModule], providers: [NotificationService] })
class NotificationsModule {}
```

A token is identified by the object itself, not by its name: two `createToken('Mailer')` calls make two different tokens, and the name only shows up in error messages. Export the token from the file that provides it and import it where it is used.

`provider(token, factory, { scope?, deps? })` builds a factory provider and checks what the factory returns against the token, so `provider(MAILER, () => 42)` is a type error. The factory can take a `resolve` function to reach other providers:

```typescript
provider(MAILER, (resolve) => new SmtpMailer(resolve(ConfigService).getOrThrow('SMTP_URL')))
```

The type flows from the token wherever it is resolved: `inject()`, `injectOptional()`, `app.get()`, `ctx.resolve()`, `Resolver` and `TestApp.resolve()`.

### Abstract classes as tokens

An abstract class works as a token too. It keeps the contract apart from the implementation without a separate token object:

```typescript
abstract class Storage {
  abstract read(key: string): Promise<string | null>
}

class MemoryStorage extends Storage {
  private data = new Map<string, string>()

  async read(key: string) {
    return this.data.get(key) ?? null
  }
}

@Module({ providers: [provider(Storage, () => new MemoryStorage())], exports: [Storage] })
class StorageModule {}

@Injectable()
class FileService {
  private storage = inject(Storage) // Storage, built by MemoryStorage
}
```

### Hints in "No provider" errors

A `hint` says where a token comes from. Pass it to `createToken()` or to `@Injectable()`:

```typescript
export const MAILER = createToken<Mailer>('Mailer', { hint: 'MailModule.configure()' })

@Injectable({ hint: 'UsersModule' })
export class UsersService {}
```

When the token is not registered, the error names its source:

```text
[Miia] No provider found for token: Mailer, required by NotificationService (NotificationsModule)
  - Mailer is provided by MailModule.configure(); import that module where Mailer is used
```

When another token with the same name and the same hint is registered, the error adds a line. Either the token is defined twice on purpose - two `defineModel('User', ...)` calls, one per connection - and this one is not registered yet, or two copies of the package that defines it are installed, each creating its own token object:

```text
  - another token named Mailer with the same hint is registered: if Mailer is defined twice on purpose (e.g. one model per connection), register this one too; otherwise two copies of the package that defines it are probably installed - deduplicate the dependency
```

## Scopes

Providers support three scopes:

| Scope | Behavior | Use case |
| --- | --- | --- |
| `singleton` (default) | One instance for the app lifetime | Services, config, repositories |
| `transient` | New instance on every injection | Stateless utilities, factories |
| `request` | One instance per HTTP request, kept on the request context | Request-scoped state, loggers |

```typescript
@Injectable({ scope: 'singleton' })
class DatabaseService {}

@Injectable({ scope: 'transient' })
class RequestParser {}

@Injectable({ scope: 'request' })
class RequestLogger {}
```

Controllers and guards are constructed once and must be singletons. The `request` scope is for providers you reach through `ctx.resolve()` or through `inject()` in another request-scoped provider.

### Request scope

A request-scoped instance lives on the request context. The first `ctx.resolve()` in a request creates it, later calls in the same request return the same instance, and concurrent requests never share one. Call `ctx.resolve()` in a handler, middleware or guard:

```typescript
import { Controller, Get, Injectable, type RequestContext } from '@miiajs/core'

@Injectable({ scope: 'request' })
class RequestLogger {
  readonly requestId = crypto.randomUUID()
}

@Controller('/orders')
class OrderController {
  @Get('/')
  list(ctx: RequestContext) {
    const logger = ctx.resolve(RequestLogger)
    return { requestId: logger.requestId }
  }
}
```

A request-scoped provider can `inject()` another request-scoped provider - both come from the same request:

```typescript
@Injectable({ scope: 'request' })
class AuditTrail {
  private logger = inject(RequestLogger) // the instance ctx.resolve(RequestLogger) returns in this request
}
```

Singletons and transients cannot `inject()` a request-scoped provider - they would keep the instance of whichever request built them. A singleton that tries fails at startup:

```text
[Miia] OrderService (singleton) injects request-scoped RequestLogger - resolve it with ctx.resolve() in the handler, or make OrderService request-scoped
```

A transient fails the same way when it is constructed, even when a request-scoped provider is the one injecting it.

Outside a request there is no instance to return, so `app.get()` and `Resolver.resolve()` throw for a request-scoped token:

```text
[Miia] Request-scoped RequestLogger can only be resolved inside a request (ctx.resolve)
```

## Optional injection

Use `injectOptional()` when a provider might not be registered:

```typescript
import { injectOptional } from '@miiajs/core'

@Injectable()
class NotificationService {
  private email = injectOptional(EmailService) // null if not registered
}
```

`null` means nothing registers the token. A token that is registered but not visible from the module - its module does not export it, or is not imported - is a [boundary violation](/docs/core-concepts/modules#the-startup-report), not `null`.

## Runtime DI introspection (Resolver)

`Resolver` is a public read-only wrapper over the DI container. Inject it when the token is not known until runtime - plugin systems, conditional resolution, dynamic factories.

```typescript
import { createToken, Injectable, inject, Resolver, type Token } from '@miiajs/core'

const PLUGINS: Record<string, Token<Plugin>> = {
  csv: createToken<Plugin>('CsvPlugin'),
  pdf: createToken<Plugin>('PdfPlugin'),
}

@Injectable()
class PluginRegistry {
  private resolver = inject(Resolver)

  load(name: string): Plugin {
    const token = PLUGINS[name]
    if (!token || !this.resolver.has(token)) {
      throw new Error(`unknown plugin: ${name}`)
    }
    return this.resolver.resolve(token)
  }
}
```

The `Resolver` exposes only read operations. Mutations (`register`, `destroyAll`) stay internal to keep the public DI surface minimal:

| Method | Description |
| --- | --- |
| `has(token)` | Returns `true` when a provider is registered for the token. |
| `resolve<T>(token)` | Resolves the provider; throws if the token is not registered. A request-scoped token throws too - resolve it with `ctx.resolve()`. |
| `resolveOptional<T>(token)` | Resolves or returns `null` for an unregistered token. |

::tip
**Prefer `inject(Token)` over `resolver.resolve(Token)` whenever you can.** Field-init `inject()` is the idiomatic MiiaJS pattern - it composes with lifecycle hooks and keeps deps explicit at the class level. Reach for `Resolver` only when the token is dynamic or you need a `has()` check.
::

## Lifecycle hooks

Singleton providers can implement four lifecycle hooks:

```typescript
@Injectable()
class DatabaseService {
  async onInit() {
    // Called during app.init() or lazily on first app.fetch(),
    // after every singleton has been instantiated.
    await this.connect()
  }

  async onReady() {
    // Called after every onInit() has completed. Guaranteed to see
    // a fully-initialized container regardless of registration order.
  }

  async onShutdown() {
    // Called during app.destroy(), before any onDestroy(). Stop taking
    // new work and wait for work in flight - stay usable for others.
    await this.drainQueries()
  }

  async onDestroy() {
    // Called during app.destroy(), after every onShutdown().
    await this.disconnect()
  }
}
```

| Hook | When called | Use case |
| --- | --- | --- |
| `onInit()` | During `app.init()` or lazily on first `app.fetch()`, after every singleton has been instantiated | Open connections, warm caches, load seed data |
| `onReady()` | During `app.init()`, after every `onInit()` has completed | Ambient discovery, cross-wiring between providers |
| `onShutdown()` | During `app.destroy()`, before any `onDestroy()` | Stop taking new work and wait for work in flight; stay usable, release resources in `onDestroy()` |
| `onDestroy()` | During `app.destroy()`, after every `onShutdown()` | Close connections, flush buffers, release resources |

All four run on singleton providers only - `transient` and `request` scopes do not trigger lifecycle hooks.

`onInit()` and `onReady()` run in dependency order: a provider's hooks run after the hooks of everything it injects - through `inject()`, a factory's `resolve()` or `Resolver.resolve()` while it is being constructed - and of everything it lists in [`deps`](#lazy-dependencies-deps). Otherwise they run in registration order, but do not rely on the order between unrelated providers: a provider pulled forward by a dependent can run ahead of one registered before it. An instance registered under several tokens gets each hook once.

The ordering gives `onReady` a guarantee `onInit` lacks: by the time any `onReady()` runs, every singleton in the container already has a fully-initialized instance, regardless of registration order. This is what makes the [Discovery Service](/docs/core-concepts/discovery) safe to use - it can scan every provider for decorator metadata at startup without worrying about which provider was registered first.

`onShutdown()` and `onDestroy()` run in the reverse order: a provider's shutdown hooks run before those of everything it injects. Shutdown goes in two phases - `onShutdown()` on every singleton, then `onDestroy()` on every singleton - so nothing is released while another provider may still be finishing its work, whether or not the two are related. That is the contract for `onShutdown()`: stop taking new work and wait for the work in flight, but stay usable - another provider may still drain its own work through yours; release resources only in `onDestroy()`.

A failing shutdown hook does not stop the rest. `app.destroy()` runs every hook, logs each failure with its source (`DatabaseService.onDestroy() failed during shutdown`), and throws once all of them have run - the error itself for a single failure, an `AggregateError` for several.

## Factory providers

Register a provider with a custom factory function. The factory's `resolve` argument reaches other providers:

```typescript
import { createToken, Module, provider } from '@miiajs/core'

export const DATABASE_URL = createToken<string>('DatabaseUrl')
export const DATABASE = createToken<Database>('Database')

@Module({
  providers: [
    provider(DATABASE_URL, () => process.env.DATABASE_URL ?? 'postgres://localhost/app'),
    provider(DATABASE, (resolve) => createDatabase(resolve(DATABASE_URL))),
  ],
})
class AppModule {}
```

### Lazy dependencies: `deps`

A factory that calls `resolve()` while it runs needs nothing more - the container sees the call and orders the hooks by it. A factory that reaches a provider later, after construction, is invisible to the container. The common case is a factory that returns a proxy resolved on first use; list what it reaches in `deps`:

```typescript
import { createLazyProxy, createToken, provider } from '@miiajs/core'

export const DB = createToken<Database>('Db')

provider(DB, (resolve) => createLazyProxy(() => resolve(DbService).db), { deps: [DbService] })
```

`deps` only orders lifecycle hooks: a provider that injects `DB` now gets its `onInit()` after `DbService.onInit()` has connected. A token in `deps` that nothing provides fails `app.init()` with `No provider found for token: X, required by deps of Y (YModule)`, and so does a cycle that exists only through `deps` (a provider lists one that injects it). Like `inject()`, a token in `deps` must be visible from the module of the provider that lists it.

The `resolve` a factory receives stays bound to its provider: called later, from the lazy proxy, it is still checked from the provider's module, not from whatever happens to be under construction at the time.
