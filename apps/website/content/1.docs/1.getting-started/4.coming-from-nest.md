---
title: Coming from NestJS
description: How NestJS concepts map to MiiaJS - injection, modules, lifecycle hooks, request scope, validation and testing.
---

MiiaJS keeps the building blocks NestJS made familiar - modules, providers, controllers, guards and decorators - on a different base: TC39 decorators without `reflect-metadata`, the Web `Request` / `Response` API, and runtimes from Bun and Deno to Node.js and edge platforms. This page maps each Nest concept to its MiiaJS form and lists what behaves differently.

## Before and after

::code-group
```typescript [NestJS]
@Injectable()
export class OrdersService {
  constructor(
    private readonly users: UsersService,
    @Inject('MAILER') private readonly mailer: Mailer,
    @Optional() private readonly metrics?: MetricsService,
  ) {}
}
```
```typescript [MiiaJS]
import { createToken, Injectable, inject, injectOptional } from '@miiajs/core'

export const MAILER = createToken<Mailer>('Mailer')

@Injectable()
export class OrdersService {
  private users = inject(UsersService)
  private mailer = inject(MAILER) // Mailer
  private metrics = injectOptional(MetricsService) // MetricsService | null
}
```
::

`inject()` runs in a field initializer while the container builds the instance, so there are no constructor parameters and no type metadata to emit.

## Concept map

| NestJS | MiiaJS | Docs |
| --- | --- | --- |
| `@Injectable()` + constructor injection | `@Injectable()` + `inject()` in a field initializer - no constructor parameters, no `reflect-metadata` | [Providers](/docs/core-concepts/providers#injecting-dependencies) |
| `@Inject('TOKEN')`, string tokens | `inject(TOKEN)` with `TOKEN = createToken<T>('Name')`. A token is a class or a `createToken()` object, never a string, and `inject()` returns its type | [Typed tokens](/docs/core-concepts/providers#typed-tokens) |
| `@Optional()` | `injectOptional(Token)` - `null` when nothing registers the token | [Optional injection](/docs/core-concepts/providers#optional-injection) |
| `useFactory` / `useValue` / `useClass` providers | `provider(token, factory, { scope?, deps?, shared? })`. The factory gets `resolve` for its dependencies; a value is `() => value`, a class is `() => new Impl()` | [Factory providers](/docs/core-concepts/providers#factory-providers) |
| `forRoot()` / `forRootAsync()` | `XModule.configure(optionsOrFactory, { global?, name? })` - one method for both: an options object, or a `(resolve) => options` factory. The factory is synchronous; async setup such as connecting happens in `onInit()`. `name` exists on the packages that support several connections or buses (drizzle, papr, mongoose, messaging) | [Dynamic modules](/docs/core-concepts/modules#dynamic-modules) |
| `forFeature()` | `register()`: `PaprModule.register([User])`, `MongooseModule.register([...])`, `ConfigModule.register(config)`. Modules that register the same token share one instance | [Papr](/docs/packages/papr#register-models) |
| `@Global()`, `isGlobal: true` | `global: true` - in `@Module({ global: true })`, on a `ConfiguredModule`, or as `XModule.configure(options, { global: true })`. Nothing is global by default, MiiaJS packages included | [Global modules](/docs/core-concepts/modules#global-modules) |
| `ConfigModule.forFeature(registerAs(...))` + `ConfigType` | `ConfigModule.register(defineConfig(name, schema))`. `defineConfig()` returns a typed token; `inject()` it to get the validated, frozen object | [Feature configuration](/docs/core-concepts/configuration#feature-configuration) |
| `ModuleRef` | `inject(Resolver)` with `has()`, `resolve()`, `resolveOptional()`, checked from the module of the provider that injects it | [Resolver](/docs/core-concepts/providers#runtime-di-introspection-resolver) |
| `DiscoveryService` | `DiscoveryService` with `getClassesWithMeta(key)` and `getMethodsWithMeta(key)` - the singletons whose class carries a metadata key, not a list of every provider | [Discovery](/docs/core-concepts/discovery#discoveryservice-api) |
| `OnModuleInit`, `OnApplicationBootstrap` | `onInit()`, `onReady()` - plain methods, no interface to implement, run in dependency order | [Lifecycle hooks](/docs/core-concepts/providers#lifecycle-hooks) |
| `OnModuleDestroy`, `BeforeApplicationShutdown`, `OnApplicationShutdown` | `onShutdown()` (stop taking new work, wait for work in flight) and `onDestroy()` (release resources). Every `onShutdown()` finishes before the first `onDestroy()` | [Shutdown phase](/docs/core-concepts/app-lifecycle#shutdown-phase) |
| `Scope.REQUEST`, `@Inject(REQUEST)` | `scope: 'request'`, `ctx.resolve(Token)` in a handler, middleware or guard, and `inject(REQUEST_CONTEXT)` in a request-scoped provider. Controllers stay singletons: a singleton that injects a request-scoped provider fails at startup instead of becoming request-scoped | [Request scope](/docs/core-concepts/providers#request-scope) |
| Interceptors, pipes, exception filters | Middleware - `app.use()` for every request, `@Use()` on a controller or method. Errors are handled with `try { await next() } catch` | [Middleware](/docs/core-concepts/middleware) |
| `ValidationPipe` + DTO classes | Route schemas: `@Post('/', { body, query, params })` with any schema that has `safeParse()`, Zod included. A failure is a 422 | [Validation](/docs/core-concepts/controllers#validation) |
| `@UseGuards()`, `APP_GUARD` | `@UseGuard()` on a controller or method, `app.useGuard()` for every matched route | [Guards](/docs/core-concepts/guards#applying-guards) |
| `@Param()`, `@Query()`, `@Body()`, `@Req()`, `@Res()` | `ctx.params`, `ctx.query`, `await ctx.json()`, `ctx.req` (a Web `Request`), `ctx.res` (a response builder) on the `RequestContext` every handler receives | [RequestContext](/docs/core-concepts/controllers#requestcontext) |
| `forwardRef()` | `forwardRef(() => X)` only for module files that import each other, on both sides. Providers need none: `inject()` runs when the instance is built, not when the file loads. A real cycle between providers is an error | [Modules](/docs/core-concepts/modules#module-files-that-import-each-other) |
| `Test.createTestingModule()` + `overrideProvider().useValue()` | `TestApp.create(AppModule).override(Token, value).compile()`; `override(XModule, XModule.configure(...))` replaces a configured module | [Testing](/docs/core-concepts/testing#overrides) |
| `app.setGlobalPrefix('api')` | `new Miia({ globalPrefix: '/api' })` - set in the constructor, before any route is registered | [Global prefix](/docs/core-concepts/routing#global-prefix) |

## What works differently

- **One container, checked boundaries.** All modules of an app share one DI container; there is no injector per module. `imports`, `exports` and `global` decide what a module may inject, and startup checks it - see [Boundaries](/docs/core-concepts/modules#boundaries).
- **One report for all violations.** `init()` collects the boundary violations it finds while it builds the singletons and throws them as [one report](/docs/core-concepts/modules#the-startup-report) before the first `onInit()`, each with its fix. A missing provider or a cycle still ends startup at once, listing the violations found so far.
- **A provider belongs to one module.** The same class in the `providers` of two modules throws (`is provided by both`) instead of creating two instances. Declare it once, export it, and import that module.
- **A module is configured once.** Configuring the same module twice throws (`is configured twice`) instead of creating a second dynamic module. Configure it once, usually in the root module, and import the class bare elsewhere. A second connection is a named variant: `DrizzleModule.configure(options, { name: 'analytics' })`. In tests, replace a configuration with `TestApp.override()`.
- **Hooks follow dependencies.** `onInit()` and `onReady()` of a provider run after the hooks of what it injects, not module by module. Shutdown runs in reverse order and in two phases: every `onShutdown()`, then every `onDestroy()`.
- **One instance per token.** There is no separate instance per importing module, and one token cannot have different implementations in different modules. A per-module variant is a separate token: a named configuration, or a `defineConfig()` token per feature.
- **A shared provider is one instance.** `register()` of the same model or config in several modules builds it once, and every one of those modules owns it - see [Shared providers](/docs/core-concepts/modules#shared-providers).
